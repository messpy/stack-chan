# CoreS3の更新

このPCでは、firmwareディレクトリから次の1コマンドで更新できます。

```sh
./scripts/update-archive.sh
```

Node・Moddable・ESP-IDFの環境を読み込み、npmの公式ラッパーで増分ビルド後、USB書き込みします。USBシリアル機器は本体1台だけを接続してください。書き込み中だけ、実行前に動作していたstackchan-hub.serviceを止め、失敗時にも再起動します。本体の再起動により、起動設定に応じて発声・会話開始する場合があります。

ビルドのみは `./scripts/update-archive.sh --build-only`。直前に成功したビルドを変更せず再書き込みする場合のみ `./scripts/update-archive.sh --flash-only` を使えます。通常は引数なしで実行してください。詳細出力はログへ保存し、端末には進行と成否だけを表示します。ログはGit対象外の `firmware/dist/update-logs/` に保存され、同時更新はロックで防ぎます。プライベートmanifestや認証情報を表示する処理はありません。ログはローカルで保管してください。

このPCのSDKパスを既定値にしています。別PCでは `STACKCHAN_NODE_BIN`、`STACKCHAN_XS_ENV`、`STACKCHAN_IDF_ENV` で変更できます。USB権限とsystemdユーザーセッションが必要です。古い生成物を毎回削除しないため、2回目以降は変更部分が中心のビルドになります。SDK・ネイティブコード変更時は時間がかかります。


## ユーザー実行で更新する運用

今後、Codexは修正とテストを終えたところで「実行待ち」と伝えて停止します。ユーザーが明示的に書き込みを依頼した場合を除き、Codexがビルドの進行を何度も確認する運用はしません。

デスクトップの「StackChan 更新」を開き、Enterで開始します。端末は準備中・ビルド中・書き込み中・復帰中・成功/失敗を表示し、最後まで開いたままになります。「StackChan_update.sh」も同じ起動用シェルです。

`firmware/dist/update-logs/latest.json` に最新の状態とログの絶対パスを原子的に保存します。`state` は `preparing`, `building`, `flashing`, `restoring`, `built`（ビルドのみ成功）, `succeeded`（書き込み成功）, `failed`。`exit_code`, `run_id`, `updated_at`, `needs_review` も含みます。電源断・強制killで途中の状態が残った場合は完了とみなさず、プロセスが残っているか確認してください。状態は `scripts/update-archive.sh --status` でも読めます。

完了したらこのチャットで「更新が終わった。ログ見て」と伝えてください。Codexはlatest.jsonを一度読み、該当ログの必要部分だけを確認します。書き込み成功は会話・タッチ・表示の実機検証成功を意味しません。端末は会話内容やAPIキーを含む可能性のある詳細ログを外部送信せず、状態ファイルにもコピーしません。

シェルはCodex CLI/APIを起動せず、ローカル処理だけで動作します。状態ファイルの変更でチャットが自動再開する連携は未設定です。

## 名前登録に失敗しても会話を続ける（2026-11-01）

人物IDが見つからない場合は、IDエラーで終了せず名前と読みで照合し直す。既存人物があればそのIDを使い、候補がなければ新しいIDを生成して登録する。AIが渡した未知のIDで新規人物を作らない。

AI経由の登録・照合が失敗したり候補が曖昧な場合は、SDへ確定人物として紐付けず、セッション内だけの名前付きゲストへ切り替えて会話を続ける。登録済みとは言わず「○○さん、よろしくね。登録はまだ確認できないけど、このままお話ししよう」と結果を返す。ボタンには名前と「仮」を表示する。人物選択から後で既存人物へ切り替えられる。結果の字幕表示に失敗してもAIへ結果を返す。

無効IDからの既存人物復旧・新規人物登録・SD失敗を再現し、失敗後にも通常の字幕と返答が処理されるテストを追加した。実機への反映はユーザー実行待ち。

## マイク変換をCへ移行（2026-11-01）

実機ログで内蔵RAMの直近空きは約84KB、PSRAMは約4.3MB。一方maxQueueLagMsは最大約1.3秒、mono送信量は5秒あたり約7～8万バイトで、16kHz・16bitの連続音声で期待する約16万バイトより少なかった。RAM枯渇と断定できるログはなく、音声経路の処理遅延を優先して調査する。

左右マイクのエネルギー集計・片側選択・4倍ゲイン・飽和・ピーク/RMS計算をJavaScriptループから `xs_archive_recognition_pcm` へ移す。Gemini workerはPCMのBase64化と送信、集計済み数値の記録だけを行う。純Cヘルパーと参照計算を、mono/stereo・空データ・音の飽和・複数ブロックサイズで比較するテストが成功。

```sh
python3 scripts/test_recognition_pcm.py -v
```

ホストテストのみ完了。ESP32ビルドと書き込みはユーザー実行待ち。実機では入力送信量、maxQueueLagMs、認識結果と次の発言への復帰を確認する。

## 名前認知の3段階と再起動対策（2026-11-01）

12:58:07の実機ログに `XS abort: native stack overflow` とソフトウェア再起動が記録された。総RAM空き容量とは別問題。SDKのESP32 main XS taskはcreation.nativeStack指定がなければ既定10KB。archive manifestのcreation.nativeStackを32KBに指定する（creation.stackは別のXS仮想スタック）。内蔵RAMへの追加負担があるため、次回ログで空き容量とnativeStackMinimumFreeの両方を確認する。

再生完了時は、AudioOutのネイティブコールバックから直接I2S終了・AudioIn作成を呼ばず、Timerの次イベントで実行する。停止済み/交換済みの出力には古い予約処理が作用しない。ホストテストでコールバック中に出力を閉じず、一回の予約後に聞き取りへ戻ることを確認した。

会話のconversationStageを `awaiting_name` → `greeting` → `conversation` として記録する。名前照合の結果は、初対面ならはじめまして、既存なら保存されている前回会話の日付を含む挨拶を返す。同じセッションで再照合しても最初の前回日時と挨拶を維持する。その後、確定人物のプロフィールと直近3件の関連履歴を参照して会話する。名前の登録/照合が失敗しても名前付きゲストとして会話を継続する仕様は維持する。

初回→再照合→次回起動相当の再会、人物確定→挨拶→2発言目の会話、音声終了時の遅延マイク再開のテスト成功。C変換版もまだ未反映のため、次のユーザー実行でまとめてビルド・書き込みする。実機の再起動解消・聞き取り精度は未確認。
