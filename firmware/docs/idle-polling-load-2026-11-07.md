# CoreS3 無操作時ポーリング軽量化（2026-11-07）

## 背景と範囲

- ユーザー報告: CoreS3が無操作中にも再起動する。原因は未確定（Issue #36, #40）。
- 起点: Draft PR #49 `fix/audio-integrity-20261105`。既存音声修正と秘密設定、公式の顔を維持する。
- **目的**: 不要なJavaScriptイベントループの起床頻度を減らす。**CPU負荷低下率やRAM改善・再起動解決は実機未実測**。

## 変更内容

| 定期処理 | 修正前 | 修正後 | 起動後の呼出頻度 | 影響 |
| --- | ---: | ---: | ---: | --- |
| USBコマンド受信 `lan-archive.js` | 5ms | **20ms** | 200→50回/秒（75%減） | 新規USB要求の検知に最大約20msの待ち時間が生じる。1周期1要求なら理論上の処理上限も低下 |
| Webサーバー起動/再試行 `archive-web.js` | 1s | **3s** | 60→20回/分 | Wi-Fi/AP利用可能後、HTTP 8082番の起動に最大約3秒かかる。起動済みHTTP要求処理の速度は変更しない |
| 背景Wi-Fi電波表示 `archive-wifi-display.js` | 2s | **5s** | 30→12回/分 | 電波強度・表示更新が最大5秒遅延。実際のWi-Fi接続処理は変更しない |

**変更しないもの（安全上の理由）**

- `archive-debug.js` の **100ms**: 障害時のUSBデバッグ排出量を減らしてログが失われるリスクを避ける。ESP32側のログキューは有界。
- `lan-archive.js` 自動オフラインの **1s**: `archive-offline-policy.js` は `age++` / `absent++` で1秒ごとのサンプル数を計時しているため、そのまま3秒化すると切替が約3倍遅れる。オフラインフォールバック要件を優先して維持。
- `archive-chat-audioio.js` 再生の **20ms**: PCM供給遅延や音切れを避ける。
- `archive-direct-chat.js` AI監視の **2s**: 音声監視のタイムアウト/状態復旧を維持（Draft #48の再接続バックオフは別PR）。
- `archive-wifi-display.js` 詳細表示画面内の **2s**: ユーザーが画面を開いている間は応答性を維持。

## 判定基準とリスク

1. **先に読み取り専用の基準値取得**: 無操作時のRAM `internalFree/internalLargest/internalMinimum/psramFree`、`boot.uptimeMs/resetReasonCode`、HTTP 8082到達性、USB操作応答時間、接続/切断イベント数。
2. **PCで検証**: JS構文チェック、既存の `npm run test:unit` とArchive回帰テスト、CoreS3 releaseクリーンビルド。ここに記したコマンドは検証計画であり、GitHub上の変更作成だけでは実行済みと見なさない。
3. **実機検証**（ユーザー承認後のみ）: 16MiBフラッシュバックアップ+SHA256、書込み、USB通信量・制御応答・起動後HTTP待ち時間・Wi-Fi表示、無操作時RAM/uptimeを旧版と比較。利用中のHTTP要求の障害がないこと、設定用APが30分で終了することを確認。
4. **障害が残る場合**: #36 のpanic/WDT/brownout/明示再起動経路および #40 のnativeメモリ所有権・リーク調査を継続。ポーリング回数が減ったことを「再起動修正完了」と扱わない。
