# アラーム通知と再起動からの復旧

2026-11-01: 予約作成は成功する一方、時刻到達後の旧 `pins/audioout` の通知音再生・終了でネイティブ例外が発生した。未完了の `pending` 予約が再起動後にも再実行され、起動ループになる経路があった。

カスタム通知音は会話音声と同じ `embedded:io/audio/out` に変更。SDから最大8192バイトずつPCMを読み、書き込み可能量だけを出力する。最後のDMA音声の再生を待ち、ネイティブの書き込みコールバックを抜けてから音声出力を閉じる。停止と読み出しエラーでも同じ終了処理を使う。

通知を始める前に `notificationStarted` を保存する。起動時にこの印がある `pending` 予約が見つかった場合、その回は自動再試行しない。単発予約は `cancelled` と理由を保存し、毎日の予約は次回分を `scheduled` に戻す。他の予約は変更しない。通知処理で捕捉したエラーにも同じ方針を使う。

旧版で既にループしている予約には開始印がないため、新版で一度試行する可能性があるが、その後の再起動から同じ回を繰り返すことは防ぐ。

確認:
- `node --experimental-vm-modules scripts/lib/archive-alarm-sound.test.mjs`: PCM順序、停止、SD読み出し異常、コールバック外での終了。
- `node --experimental-vm-modules scripts/lib/archive-offline.test.mjs`: 通知中断後の復旧、毎日予約の維持、関係ない予約の維持、復旧の繰り返しに対する安定性。
- 実機: 2026-11-01 23:24〜23:25 JST、8秒タイマーと12秒先の単発アラームを会話モードONの状態で通知・停止。両方 `fired`、通知音停止後もUSB操作と会話待機が継続、再起動なし。既存の「毎日のアラーム」「朝のアラーム」は維持。
- 音声での予約作成: 試験環境のPC出力が `auto_null`、ALSAから利用できるサウンドカードなし。読み上げを本体へ実際に聞かせられなかったため未検証。会話へのツール登録と `callDeviceTool` へのルーティングはコード上存在するが、実音声での成功を意味しない。
- 最終書き込み `20261101-232723-10731` 成功。23:29 JST に再度タイマー・アラームを通知・停止し、双方 `fired`、通知音のエラー・panic・再起動なし。既存2件の予約は `scheduled` のまま。
